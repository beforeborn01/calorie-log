# 交叉评审 — 20260605-110404

- **评审任务:** 对微信小程序 calorie-log-miniprogram 的【信息架构与产品设计】做评审与辩论，给出最终结论。这是产品/IA 层面的评审，不是代码 bug 审查。

## 背景：这是一个叫"食养记"的卡路里/健身饮食记录小程序
当前底部 4 个一级 tab（见 app.json tabBar）：
- 首页 pages/home/home —— 今日饮食录入 + 热量进度环 + 热量收支(日常消耗/运动消耗/净消耗) + 经验卡 + 餐饮记录列表；右上角一个小按钮进入"分析"
- 记录 pages/history/history —— 历史饮食记录，可切日期，增删改
- 运动 pages/training-quick/training-quick —— 运动速记，页面内还有二级 tab：速记/计划/历史/统计
- 我的 pages/profile/profile —— 资料卡 + 经验卡 + 8 项功能菜单(健身目标/体重体脂/周月报告/运动计划/运动统计/好友/排行榜/设置)
其他页：pages/statistics(每日分析:评分+建议+营养)、reports(周月报告)、body(体重体脂)、goal(健身目标)、social-*(好友/排行)、training-plans/sessions/stats。

## 已识别的 7 个问题（请逐条证实或反驳，并补充遗漏）
1. tab 权重与价值倒挂：核心价值"分析"只在首页右上角小按钮，低频的"记录"却占一级 tab。
2. "记录"tab 与首页严重重叠：首页锁今天后是"饮食录入+列表+增删改"，记录 tab 是同套 UI 换成可切日期，仅多"切日期"。
3. 洞察类功能四散无统一入口：记录流水、每日分析、周月报告、体重趋势分散在 4 处。
4. 同一功能多入口、层级不一致：运动计划/运动统计在"运动 tab 内"和"我的菜单"各有一个；经验卡在首页和我的重复。
5. "健身目标"是所有数字(目标热量/营养比例/净消耗)的源头，却埋在"我的"二级菜单，可见性过低。
6. 两个核心行为(吃/练)结构不对称：饮食有今天+历史两页，运动只有一页+内部二级 tab。
7. "我的"是大杂烩：配置/洞察/社交三类混在一个 8 项菜单里，无分组。

## 待评判的重构建议（请评估其合理性、风险、是否过度设计，并给替代方案）
把心智从"按数据类型分(饮食/运动)"改为"按用户意图分"，建议新 4 tab：
- 今天：饮食进度+运动概要+热量收支+快捷录入
- 记录：按日期统一查看/录入 饮食+运动（合并现 history 与运动历史）
- 洞察：每日分析+周月报告+体重趋势+运动统计/PR 的中心
- 我的：资料 + 健身目标(置顶) + 社交 + 设置
关键取舍：这会把"运动"从一级 tab 降级。备选方案：保留运动一级 tab(今天/记录/运动/我的)，把"洞察"做成今天页醒目入口而非 tab。

## 落地优先级（请评估排序是否合理）
1.立即:把"分析"提为显眼入口或换掉"记录 tab"  2.小:"我的"菜单分组+目标置顶  3.小:去重复入口  4.中:合并饮食/运动历史  5.中:搭"洞察"中心

## 第 0 轮 —— 独立盲审

### 评审人 A (Claude Code)

以下为基于实际代码（app.json tabBar、home/history/training-quick/profile 各页 wxml/js）的 IA 评审结论。

1. [MAJOR] app.json:37-40 tabBar 四个一级入口 — "tab 权重与价值倒挂"成立，但表述需修正：问题不是"记录占了 tab"，而是"分析（statistics）根本不在导航骨架里"。
   home.wxml:7 中"分析"是一个 `btn-sm btn-ghost` 文字小按钮，挤在标题行右上角，零图标、低对比、易被当作次要操作；而 statistics 是该产品唯一的"评分+建议+营养"价值输出页。一个一级心智的功能被降到比 FAB 还弱的视觉层级，这是真实的价值-曝光倒挂。

2. [MAJOR] home.wxml:66-85 vs history.wxml:14-22 "记录 tab 与首页重叠" — 成立，且重叠度比描述更高：两页的餐次卡片、record-row、改/删按钮、空态、添加按钮是逐字段同构的。
   唯一实质差异是 history.wxml:4-10 的日期 picker + 前/后一天，以及 summary 用 grid-2（home 用进度环）。home.js 锁定 today、history.js 用 `dateUtil.today()` 起步可切日期——history 是 home 的超集减去进度环/收支/经验卡。维持两个近乎同构的录入页会持续产生双倍维护成本（任何餐次交互改动要改两处）。

3. [MINOR] 问题3"洞察四散无统一入口" — 部分成立但被轻微夸大。
   流水（history）、每日分析（statistics）、周月报告（reports）、体重趋势（body）确实分散，但"流水"本质是录入产物而非洞察，把它算进洞察类是混淆。真正分散的是 statistics / reports / body / training-stats 四个**只读分析页**，其中三个埋在 profile.js:15-17 菜单、一个在 home 右上角——这才是核心痛点，建议聚焦于此而非把 history 也拉进来。

4. [MINOR] profile.js:16-17 vs training-quick.wxml:7-9 "多入口、层级不一致" — 成立但属低危。
   运动计划/统计在"运动 tab 二级 nav"和"我的菜单"各一份；经验卡在 home.wxml:55-64 与 profile.wxml:20-22 重复。但重复入口对用户是冗余容错（多路可达），伤害有限；经验卡重复甚至有动机一致性。真正的不一致风险是：同一目的地从不同入口进去后返回栈/选中态不一致，而非"有两个入口"本身。

5. [MAJOR] profile.js:13 "健身目标埋在二级菜单" — 完全成立，是 7 条里仅次于第 1 条的严重项。
   goal 是 home 进度环目标值、净消耗、营养比例（macroStats/netStats）的唯一数据源头。当前它是 profile 菜单第一项 `/pages/goal/goal`，从 home 到它需"我的 tab → 滚动找菜单 → 点进"。源头配置可见性过低会直接导致新用户看到的是默认/空目标，进度环失去意义。这条应与第 1 条并列为立即处理项。

6. [MINOR] training-quick.wxml:5-10 "吃/练结构不对称" — 现象属实，但定性应反转：不对称恰恰是运动侧的**正确解法**，饮食侧才是问题。
   运动用页内 sport-nav（速记/计划/历史/统计）把一类行为的录入+历史+分析收敛在一个 tab 内，信息密度高、跳转少；饮食却把今天(home)与历史(history)拆成两个一级 tab。与其说"运动缺了一页"，不如说"饮食多占了一个 tab"——应让饮食学运动的收敛模式，而不是反过来给运动加页。

7. [NIT] profile.wxml:23-26 / profile.js:12-21 "我的是大杂烩" — 成立但为最低优先级。
   8 项菜单（目标/体重/报告/运动计划/运动统计/好友/排行/设置）确实混了配置、洞察、社交三类且无分组，但 8 项尚在可扫描范围内，纯属体验打磨。加 section 分组成本极低、收益小，不应排在结构调整之前。

8. [MAJOR] 遗漏的更严重问题：home 与 history 的"今天"在 onShow 各自独立拉取、各自维护 daily/meals，状态不共享。
   home.js 锁 today、history.js 也默认 today，用户在 history 改了今天的记录、切回 home tab 时依赖 home 自己的 onShow 重新 load 才能一致。双页同写"今天"是数据一致性与心智双重负担——这比"tab 排序"更能论证 home/history 必须合并或彻底差异化（见第 11 条）。

9. [MAJOR] 遗漏问题：导航深度对核心录入路径不利。home.wxml:73/87 录入要 `navigateTo` 到 add-food，运动录入却在 training-quick 页内直接表单提交（training-quick.wxml:16-22）。
   两个核心行为（吃/练）的录入摩擦不对称：吃要跳页、练在原地。对"以饮食为主轴"的产品，主轴行为反而路径更长，这是比 tab 命名更实际的转化损耗点。

10. 【问题 B 裁决】[MAJOR] 推荐：**保留运动一级 tab（备选方案），不要新 4-tab 降级运动。**
   理由：①把运动从一级 tab 降为"记录/洞察里的一类数据"会破坏 training-quick 已经做对的"页内收敛"模式（第 6 条），把一个自洽的功能拆散重组，是为对称而对称。②"以饮食为主轴"恰恰意味着饮食该收敛、运动维持独立，而非把两者揉进通用"记录/洞察" tab——通用 tab 会让两类录入表单都变二等公民（第 9 条）。③新 4-tab 的"记录"= 合并饮食+运动历史，但二者数据模型、编辑交互完全不同（record-row vs sets×reps），强行同页只会做出一个带切换器的拼接页。明确推荐：tab 保持「今天 / 运动 / 洞察 / 我的」，删掉独立"记录 tab"（其能力并入"今天"），新增"洞察"承接 statistics/reports/body。

11. 【问题 C 裁决】[MAJOR] home vs history 重叠：**删 history 作为一级 tab，把"切日期"能力下放进 home。**
   差异化方案：home 顶部日期默认 today 且可点开 picker 回看历史日（复用 history.js 的 onPrevDay/onDateChange 逻辑），历史日时隐藏"热量收支/经验卡"只留录入+汇总。这样一份录入 UI 服务全部日期，消除第 2、8 条的同构与状态双写。history 页可作为非 tab 的二级页保留或直接退役。不要"两个都差异化保留"——那只是把重叠改名，维护成本不变。

12. 【问题 D 裁决】[MINOR] 落地优先级排序基本合理，但第 1 步选错了对象。
   现排序把"换掉记录 tab"和"提升分析"并列第一。但"换 tab"是结构破坏性改动（影响所有用户肌肉记忆，需回归测试），而"目标置顶+可见"（第 5 条）和"分析提为显眼入口"（第 1 条）是低风险高收益的纯增量。建议第一步只做：①home 右上角"分析"从文字小按钮升级为带图标的醒目入口；②goal 在 profile 置顶或在 home 空目标时给引导卡。把"动 tab 结构"后置到这两步验证数据后再做。

13. 【问题 E 裁决】[MAJOR] "新 4-tab 合并饮食/运动历史"是典型过度设计/伤现有习惯。
   两类记录交互异构（第 10 条），合并需要页内再切换，等于用一个二级切换器换掉一个一级 tab——总跳转数不降反升；且老用户"运动在第三个 tab"的肌肉记忆被打断。同样，第 7 条"我的分组"在结构问题解决前去做属于打磨错位。真正零争议、该最先落地的反而是优先级里排在后面的"去重复入口"（第 4 条）与"目标置顶"（第 5 条）。

14. [NIT] 全局命名：home 标题"今日食养"（home.wxml:6）、tab 名"首页"、kicker "TODAY" 三套叫法指同一页；statistics 被称"分析"但页面与 tab 均无"分析"锚点。
   若推进重构，建议先统一术语（tab"首页"→"今天"，与 kicker 一致；为 statistics 确立稳定名"分析/洞察"），术语统一是 IA 重构的零成本前置，且能独立于结构改动先行。

15. [MINOR] 可测试性缺口：以上所有 IA 判断（"分析低频/记录低频""目标可见性过低"）目前都是主观断言，仓库内无任何 tab 点击/页面停留埋点佐证。
   在动一级 tab 这种高风险改动前，最该补的是 home"分析"按钮点击率、history tab PV、goal 页到达率三个指标——否则第 1/2/5 条的"价值倒挂"无法证伪，重构是在赌而非在测。建议把"补埋点"作为真正的第 0 步。
